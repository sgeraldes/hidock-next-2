## Console and physical access

The new [Windows inventory](../../research/rea/access-transfer630-lab/windows-device-inventory.json) observes the normal Jensen USB node and audio endpoints, with no COM ports currently enumerated. It opened no device handle. This does not establish that the console lacks physical UART pads or that another mode cannot expose a console.

The compiled console binds UART_0. Establish its exact driver configuration, effective runtime baud and accessible electrical route from target evidence. Do not assume a generic115200-baud/3.3V pinout from a related board. The first connected command must be a qualified harmless prompt/help/status query; arbitrary registered callbacks can write state or reboot. A USB bridge, if implemented, needs request correlation, bounded buffers/output, finite execution and explicit separation from audio/transfer/OTA ownership. The bounded f117 USB bridge is implemented and its three393986 status requests are physically observed. Arbitrary console callbacks and physical UART access remain separate unqualified work.

## Listing/download protocol and tests

All command numbers in this section are **decimal**, with hex given to prevent confusion with live control0x0021:

| Command | Recovered role | Needed qualification |
| --- | --- | --- |
|4 /0x0004|Whole catalog; six-byte prefix and 57-byte entries|Empty/one/many files, split headers/entries, opaque six-byte entry gap, duplicate/invalid names, incomplete scan, count drift and cancellation|
|6 /0x0006|File count|Agreement with the actual listing filter; unknown/error distinguished from confirmed zero|
|5 /0x0005|Whole-file stream|Exact expected logical bytes, EOF/failure, delivery padding, truncation/overshoot, drain after cancel and disconnect|
|13 /0x000d|BE32 byte count + filename, starts at byte0|Correct short/prefix read; raw payload rather than generic ACK; no fake seek API|
|21 /0x0015|BE32 byte offset + BE32 byte count + filename|Range start/end/EOF, offset/count overflow, varied sizes, aligned/unaligned reads, repeated ranges and reconstruction versus whole-file download|
|26 /0x001a|BE32 first **entry index** + BE32 **entry count**|Page boundaries/cache lifecycle; prefix is four-byte total count, not CMD4's six-byte prefix;57-byte entries. Do not use byte offsets here.|

This separates offset-based file reads from entry-based cached listing. Neither is a general-purpose recording-file upload API.

The [earlier transfer audit](../../research/rea/access-transfer630-lab/transfer/REPORT-TRANSFER630.md) reproduced three host discrepancies: an empty CMD4 catalog waited for the ten-minute watchdog, standalone CMD5 accepted bytes above the expected size, and queued registration could replace active cancellation ownership. Later host fixes and native/controller regressions are recorded in the [protocol completion report](../../research/rea/completion630-lab/protocol/REPORT-PROTOCOL-COMPLETION630.md), with [stock app observations](../../research/rea/completion630-lab/runtime/REPORT-STOCK-APP.md) covering normal resume, cancellation and drive lifecycle. Keep these historical failures; do not present them as the current implementation. The intermittent cold first-page count mismatch remains unresolved despite subsequent successful reconnect/page runs. A partial listing must still carry incompleteness explicitly so reconciliation cannot treat missing files as deleted, and progress counts delivered payload/file bytes. The [detailed test matrix](../../research/rea/access-transfer630-lab/transfer/TEST-MATRIX.md) retains remaining protocol, writer, controller and hardware cases.

The catalog's 16-byte MD5 signature is intended to cover the first 1 KiB, not the whole file. The original helper can hash unread scratch bytes after a positive short read; upload 2 corrects the actual byte count in offline native tests, with physical556-byte whole-prefix and 2092-byte first 1024 metadata equality now observed. Other error/race modes remain unqualified. Validate the prefix independently, preserve it as partial integrity evidence, and calculate full downloaded SHA256 locally. A prefix match alone cannot attest an unchanged full remote file or replace full-versus-range/golden-copy comparison. [Metadata fix and oracle](../../research/rea/completion630-lab/firmware/generation-upload2/metadata-verification.json).

Resume requires a durable download journal binding dock identity, filename, size, stable file version/evidence, committed byte ranges and hashes. Verify that the remote file is unchanged before reusing a prefix; growing/current recordings are not stable resume targets. Advance the journal only after the file writer commits. On uncertainty drain/quarantine through the owner before any retry. Resume CMD21 ranges only after range behavior is qualified; do not describe existing CMD5 restart-from-zero as resume.

Use a protected manual-only test recording or a known test-medium fixture. Obtain an independent golden download where possible, reassemble ranges into the identical full-file SHA256 and decode the result. Record physical USB frame-size histograms, wall time, time to first byte, effective payload throughput, parser/IPC/disk time, peak buffered bytes and owner settlement time. Include many small files, a larger file, a slow local writer, interrupted process/USB session and post-reconnect resumption. Synthetic filesystem timing supports design decisions but does not measure the dock.

## Drive options and order

The [access audit](../../research/rea/access-transfer630-lab/access/REPORT-ACCESS-PATHS.md) finds `udisk`/MSC handlers and an entry command. A mode request ACK proves the request path, not a mounted SD drive. Before testing the mode on the everyday dock, qualify backend-to-SD mapping, active recording/file handles, media exposure, filesystem cache consistency and an expected source-backed exit procedure; then demonstrate the actual exit on suitable controlled hardware. A zero byte to0xf00f must not be invented as an exit command. Standard-looking SCSI eject code is not proof that its callback returns the dock to Jensen mode.

A virtual read-only drive is a separate useful path. [WinFsp](https://winfsp.dev/) supplies Windows filesystem APIs; [Microsoft ProjFS](https://learn.microsoft.com/en-us/windows/win32/projfs/projfs-programming-guide) can project provider data as files/directories beneath a folder. Those are available implementation frameworks, not installed/working HiDock adapters. A drive-letter mount requires the selected framework/mount implementation; a synced local folder alone is only a mirror.

Keep one Jensen owner behind the facade; coalesce concurrent requests, serialize device reads, use a bounded range cache and reject all writes/deletes initially. Handle Explorer/player random reads, nonexistent names, Windows filename collisions, EOF and unplug/offline state honestly. Preserve exact remote names internally. Cached access improves repeat-read latency; it does not increase the device's physical link throughput. Benchmark both native MSC and the Jensen path before claiming one is faster. Write access remains separate work because ordinary Jensen file reads do not supply a general file-write/rename protocol.

These are parallel workstreams with concrete dependencies, rather than one prerequisite that silently postpones the rest. First implementation priority is listing/download correctness and range/resume, while console and native-drive reachability analysis proceeds independently.
