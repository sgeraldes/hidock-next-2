# Firmware recording format and duration delivery

The download completion path detects the actual file container instead of assuming every device `.hda` is a WAV. Raw MPEG Layer III content is saved as `.mp3`; PCM WAV content remains `.wav`. The device's original filename is retained for synchronization. After the recording row is inserted or updated, duration is measured from the saved file, with provenance `file`. Measurement failure does not discard a successful save or fabricate a duration.

The focused independent boundary check exercised the actual `saveRecording` and `markRecordingDownloaded` functions against temporary files and SQLite 3.53.4. Configuration and database-path scaffolding were isolated; those functions, the database and duration parser were not mocked. A generated 16,704-byte MP3 fixture measured two seconds, and a PCM WAV measured one second. Existing-row identity survived the update; invalid audio still produced a saved row with unknown duration. Saved bytes were exact, and no partial files remained. No user recording was altered by this check.

A separate Sonnet delivery exercised the current shared working-tree staged-file path against real files and SQLite: Buffer MP3 measured 18 seconds, existing-row PCM WAV two seconds, and staged MP3 nine seconds with staged cleanup and exact-byte preservation. This supplements the independently executed HEAD-compatible publication; it does not make the unrelated staged-download implementation part of this delivery.

Source and tests are published on `fix/download-duration-format-20261013`, starting at commit `1757282f2393bb8d93c6c9d4dd239855a2486699`. Publication uses a separate Git index so unrelated main-branch and working-tree changes are excluded.

Its focused failure test forces a measurement exception and verifies success, the warning and queue continuation. Both handler changes are published on the same isolated delivery branch; unrelated metadata IPC changes remain excluded.

The existing Rec07 library row was corrected separately and its duration/provenance were read through the running app API earlier in the day. No fresh physical dock download was performed for this delivery.
