# CK802 profile review for the VAD source candidate

**Status: PARTIALLY VERIFIED.** The repository carries strong CK802 build-profile evidence for the H1E images, but the retained VAD integration ELF was built with `-mcpu=ck803`. This report is a source and artifact audit only; I did not compile a CK802 variant or qualify physical silicon. The isolated CK802 compile/link is being checked separately.

## Target evidence and the existing build

The latest pinned official H1E 6.3.0 decoded image is SHA-256 `5f8ba521c9cdec6eb25d84825f248543c81e8f0daa96094bdb705a53f7e673ce`. Its retained marker-rules report identifies a 1,360-byte little-endian CK802 module at `0x0112a000`, SHA-256 `2c5e3c9660f5e50099f822828e3a515705657b9394d8aad863fd9db486736ead` (`research/rea/evidence/h1e-6.3.0-marker-rules/REPORT-MARKER-RULES.md:5`). That module's ELF attributes name both `ck802` and ISA flags `0x2806` (`attributes.txt:23-25`). The frozen 393988 generation-restore4 system is a separate offline candidate, decoded SHA-256 `b338e4d5e7d456dd2b7a0048bb8e2c338e2464ad25029267b5e46cb4ad880c2f`; its ELF metadata also reports CK802/`0x2806` (`generation-restore4/REPORT-RESTORE-EXTENSION.md:5`, `generation-restore4/elf-metadata.txt:51-55`). The board defconfig and retained sample `.config` select `CONFIG_CPU_CK802=y` (`research/rea/references/build-contracts/boards--csky--ats2853p2_evb--ats2853p2_evb_defconfig:2-3`, `samples--bt_speaker--outdir--ats2853p2_evb_285l2--.config:33-35`). These identify the repository's target build profile; they do not prove which core is physically present in a particular device.

The latest VAD conditional link review is dated 2026-10-13. Its recipe compiles every C and assembly input with `-mcpu=ck803` (`native-link-candidate/build-offline.sh:35,54-56`), and the review explicitly calls the result source-only and not target-qualified (`LINK-REVIEW.md:9`). The receipt marks hardware testing, installation and release approval false (`output/link-receipt.json:2-7`). Therefore the current VAD objects, instruction stream, ABI output, and successful link cannot be carried forward as CK802 results.

## Concrete CK802 instruction/link gate

The CK803 linked disassembly contains `divu` in `decimal()` at `0x0112f5e0` (`candidate.objdump.txt:639`); this helper is used by the existing f117 version/uptime formatting in `console630_f11a.c:48-58`. The current integration script links with `ld -nostdlib` and does not add libgcc (`build-offline.sh:57-63`). Separately, the retained CK802 generation-restore4 link map pulls `_udivsi3` and `_umodsi3` from the CK802 `libgcc.a` (`generation-restore4/guard630.map:3-6,133-138`). This does not by itself prove `divu` is unsupported by CK802, but it makes division lowering and runtime-helper resolution a specific compile/link check: if CK802 emits helper references, this current `-nostdlib` link will fail unless the intended CK802 helpers are included or that code path is excluded. The CK802 marker-rules disassembly not showing a mnemonic is not proof that the ISA lacks it.

The same check must cover VAD's 64-bit timestamp helpers (`vadt_age` and `vadt_encode_reply_with_age`) even though the current snapshot path is explicitly unclocked. Confirm whether CK802 emits inline sequences or helper references, and inspect the final map for only intended CK802 multilib inputs. The compiler output must identify `ck802`/ISA flags `0x2806`; inspect the final disassembly for any target-specific instructions the CK802 assembler accepted but whose execution support has not been established by the pinned target evidence.

The independent isolated comparison artifacts are now present under `native-ck802-candidate/`. The CK802+libgcc receipt reports a successful conditional offline link with `hardware_tested`, `installed`, and `release_approved` false; `sections.txt` identifies CK802/`0x2806`, and both pre/post input checks match all 36 accepted inputs (`output-ck802-libgcc/link-receipt.json`, `sections.txt`, `input-check.txt`, `input-check-post.txt`). It compiled the poll, loader, frame, guard, constructor and native-hook inputs with `-mcpu=ck802`; this is useful source/compiler evidence, not execution evidence. Its build script changes the CPU flag but still omits the SDK flags listed above (`build-ck802.sh:35-47`), so enum and character ABI parity remains unverified. The separate `output-ck802` directory has no completed receipt or ELF, so I cannot state its terminal link result from retained artifacts.

The successful map makes the division dependency concrete: `console630_f11a.o` references `__udivsi3` and `__umodsi3`; CK802 multilib resolves them at `0x0112f978` and `0x0112f9c4` respectively (`output-ck802-libgcc/candidate.map:3-6,72-77`). The CK802 disassembly calls the modulo helper at `0x0112f5be` and the division helper at `0x0112f5ce` (`candidate.objdump.txt:715-722`). That confirms the deliberate libgcc link requirement for this dispatcher source under the observed profile; it is not an unsupported-instruction finding. The VAD code paths also compiled in that recipe, but their CK802 ABI-flag parity and runtime behavior remain separate from this link success.

## Required closure evidence

1. Compile **all** VAD C and assembly inputs using the SDK's CK802 flags, not only the poll and guard objects; verify enum-bearing interfaces, character semantics, structure assertions and assembly-facing integer signatures are consistent.
2. Link with the actual CK802 multilib policy, inspect undefined symbols and the map, and resolve any `__udivsi3`, `__umodsi3` or 64-bit helper references deliberately.
3. Record CK802 ELF attributes and inspect disassembly for the poll wrapper, snapshot/guard, constructor stub, native hooks and all generated helper code; recheck branch relocations and `r0` return flow.
4. Keep the constructor's `r7` preservation across unresolved ROM/indirect callees as an independent open ABI assumption. A clean CK802 compile/link cannot prove those runtime callees preserve it or qualify hardware behavior.

No CK802 build, firmware generation, installation or device test was performed for this audit. The current result is source-level compatibility guidance, not a target-qualified VAD implementation.
